## Demo flow (matches the 7-minute script)
1. The JD text box is pre-filled from `data/dataset.json`. Click **Extract rubric**.
2. Expand a couple of requirements to show `keywords` (what a keyword ATS looks for) vs `equivalents` (what it misses).
3. Click **Run Second Look on all candidates** — watch the progress bar (16 candidates, ~50s).
4. Point at the two shortlist columns: ATS baseline vs Second Look, and the 🟢 RESCUED badges.
5. Point at the live eval line: hard-rescue recall / false rescues / grounding rate — computed from this exact run, not hardcoded.
6. Open a rescued candidate in the selectbox, show the evidence quotes, bias signals, interview questions.
7. **Judge's turn**: clear the JD text box, paste a totally different JD (any role), click Extract rubric, Run again. This proves it's not hardcoded — already verified live with a Data Analyst JD against the same backend-engineer CVs: everyone correctly scored near zero.

## If the API hiccups mid-demo
Gemini's `flash-lite-latest` occasionally 503s under load; the app retries automatically (up to 6x with backoff) and shows a clean error + "click again" message if it still fails — cached candidates from that run are not re-scored, only the one that failed.

## Assumptions to state at the demo
1. Synthetic CVs/JD only, generated by Gemini; no real personal data.
2. CVs are plain text for this prototype (no PDF/DOCX parsing) — stated simplification, not a blocker.
3. Recommends a human second review; never auto-rejects/auto-hires.
4. Bias flags are signals for a reviewer, not a legal bias audit.
5. The keyword baseline imitates a typical ATS knock-out filter; real ATS logic varies by vendor.
